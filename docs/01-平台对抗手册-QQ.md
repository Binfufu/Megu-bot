## 1. 凭证与令牌

| 项 | 事实 |
|---|---|
| `AppID` | 开放平台"开发设置"里拿。**不是保密信息** 📄 |
| `AppSecret` / `ClientSecret` | 用于换 token。**等同密码** 📄 |
| 获取 token | `POST https://api.bot.qq.com/app/getAppAccessToken`,body `{appId, clientSecret}` 📄 |
| 返回 | `{access_token, expires_in}` —— **`expires_in` 可能是字符串 `"7200"`**,要 `Number()` 转 ✅ |
| 有效期 | 默认 7200 秒;过期前 60 秒内请求会拿到新 token,旧的这 60 秒内仍有效 📄 |
| 刷新策略 | 自己缓存 + 提前 60 秒刷新。**不要每条消息都去换** ✅ |

### ⚠️ 坑:失败时 HTTP 仍是 200

`getAppAccessToken` **业务失败时 HTTP 状态码是 200**,错误在 body 的 `code` 字段:

```json
{ "code": 100016, "message": "invalid appid or secret" }
```

**所以判断成功不能只看状态码。** 必须同时检查 `code` 和 `access_token` 是否存在。✅

常见 code:`100001` 太频繁 / `100007` appid 无效或机器人被封 / `100016` appid 或 secret 不对 / `10004` 机器人不存在 📄

## 2. 鉴权格式:两个 token 长得像,但用在不同地方

这是**最容易搞混的一点**:

| 用途 | Header / 字段 | 格式 |
|---|---|---|
| 调 OpenAPI(发消息等) | `Authorization` 请求头 | **`QQBot {ACCESS_TOKEN}`** 📄 |
| WebSocket 网关鉴权 | Identify 的 `d.token` | **`QQBot {AccessToken}`** 📄 |

### ⚠️ 坑:老文档写的是另一种格式

部分老页面仍写 `Bot {appid}.{app_token}`。**这个方式已废弃** —— 官方"启动接入"页原文:

> Token 的鉴权方式已废弃,请使用更安全的 `Access Token` 鉴权方式。

**如果你照老文档实现,会一直鉴权失败。** 以"事件订阅 → WebSocket 方式"页为准。✅

## 3. 网关连接

### 地址是动态的,不要硬编码

调 `GET /gateway/bot`(或 `/gateway`)拿地址。**实测解析到的是 `wss://api.sgroup.qq.com/websocket`**,
而**不是**文档示例里写的 `wss://api.bot.qq.com/websocket/`。✅

> **教训:凡是文档给了"示例地址"的地方,都去调接口拿真的。** 这一条几乎对所有平台成立。

### 连接生命周期

```
建立 WS → 收 op 10 Hello(含 heartbeat_interval,实测 45000ms)
        → 发 op 2 Identify { token, intents, shard:[0,1], properties }
        → 收 READY(含 session_id 和机器人自己的 id/username)✅
        → 按 interval 发 op 1 心跳(d = 最新的 s)
        → 收 op 11 Heartbeat ACK
```

| opcode | 名称 | 方向 |
|---|---|---|
| 0 | Dispatch(事件) | 收 |
| 1 | Heartbeat | 收发 |
| 2 | Identify | 发 |
| 6 | Resume | 发 |
| 7 | Reconnect | 收 |
| 9 | Invalid Session | 收 |
| 10 | Hello | 收 |
| 11 | Heartbeat ACK | 收 |

### 重连与恢复

- 断线后短时间内重连会**补发遗漏事件**,用 `op 6 Resume` 带 `session_id` + `seq` 📄
- **实测:网关会主动发 `op 7` + 关闭码 `4009 Session timed out`,这时应该 Resume 而不是重新 Identify** ✅
- `shard` 不分片就传 `[0,1]`

### 关闭码速查

| 码 | 含义 | 能不能 Resume | 能不能 Identify |
|---|---|---|---|
| 4006 | session id 无效 | 否 | **是** |
| 4007 | seq 错误 | 否 | **是** |
| 4008 | 发包过快 | **是** | 是 |
| 4009 | 连接过期 | **是** | 是 |
| 4013 / 4014 | intent 无效 / 无权限 | 否 | 否 |
| 4914 | 机器人已下架,只能连沙箱 | 否 | 否 |
| 4915 | 机器人已封禁 | 否 | 否 |
| 4900~4913 | 内部错误 | 否 | **是** |

📄 来源:WebSocket 方式页的错误码表。

## 4. Intents:一个位管一类事件

我们只需要 **`GROUP_AND_C2C_EVENT (1 << 25) = 33554432`**,它一次覆盖:

- `C2C_MESSAGE_CREATE` — 单聊
- `GROUP_AT_MESSAGE_CREATE` — 群里 @ 机器人
- `GROUP_MESSAGE_CREATE` — **群全量消息**
- `FRIEND_ADD/DEL`、`GROUP_ADD_ROBOT/DEL_ROBOT`、`GROUP_MSG_REJECT/RECEIVE`、`C2C_MSG_REJECT/RECEIVE`

### ⚠️ 坑:特殊事件需要申请,而且权限被取消时"静默失败"

文档原文:

> 除了 `GUILDS`、`PUBLIC_GUILD_MESSAGES`、`GUILD_MEMBERS` 是基础事件…**其他特殊事件都需要经过申请**…
> **如果拥有的某个特殊事件类型的权限被取消,则在当前连接上不会报错,但是将不会收到对应的事件类型。**

**所以"突然收不到消息"可能是权限被回收,而连接看起来完全正常。**
排查第一步永远是:**日志里到底有没有那条事件**。✅(这条经验救过我们两次)

## 5. 🔥 最大的坑:全量模式开关在**群设置**里,不在控制台

这是本次接入最耗时间的一个误解。

### 事实

**QQ 群 → 群设置 → 选中该机器人 → 「机器人可获取的群聊消息范围」→「获取群内全部消息」**

三条硬约束:

1. **只有群主能改**(管理员也不行)
2. **每个群要单独设一遍** —— 不是一次性开关
3. 部分"快速创建"的机器人页面会显示「暂不支持进入群聊」,那就无解

### 为什么容易误判

- 官方文档**只描述了 `GROUP_MESSAGE_CREATE` 这个事件**,从没说开关在哪
- 很容易误以为它和 Intent 一样在开放平台控制台里申请
- **Intent 确实不用改**(同一个 `1<<25`),但开关不在同一层

### 症状识别

| 症状 | 判断 |
|---|---|
| 日志里只有 `GROUP_AT_MESSAGE_CREATE`,没有 `GROUP_MESSAGE_CREATE` | 全量模式**没开** |
| 群里发图但机器人没反应 | 大概率同上 —— **事件根本没送到**,不是下载失败 |
| 文档说支持,实际收不到 | 先去群设置确认,再怀疑代码 |

> 📌 来源:官方文档没写,MaiBot 的 QQ 官方适配器文档写了完整操作步骤。

## 6. 🔥 第二大的坑:三个 id 空间不互通

| id | 什么时候出现 | 含义 |
|---|---|---|
| `user_openid` | 单聊事件 | 该用户在此 bot 下的唯一标识 📄 |
| `group_openid` | 群聊事件 | 该群在此 bot 下的唯一标识 📄 |
| `member_openid` | 群聊事件 | 该用户**在此群内**的唯一标识 📄 |
| `user.id`(READY) | 网关鉴权成功 | **机器人的全局 id** |

### 踩过的具体 bug

我最初判断"是否被 @"的方式是:**拿 READY 里的机器人 `user.id`,去比对消息的 `mentions[]`**。

**永远匹配不上** —— READY 给的是全局 id,群里的 mention 用的是**群内 `member_openid`**。结果:**每一条 @ 都被判成"没被 @"**,机器人彻底不回话。

### 正确的判定(多信号)

| 信号 | 可靠性 |
|---|---|
| `mentions[]` / `msg_elements[].author` 里的 id 精确匹配 | 高(但群里通常匹配不上) |
| **`bot: true` 标志** | **群里实际生效的就是这个** |
| 文本里残留的 `<@!xxx>` | 兜底 |

群里一般只有一个机器人,所以 `bot: true` 在实践中够用。

### 另一条:不同 bot 拿到的 openid 不同 📄

> 不同 `bot` 在单聊场景获取到的用户唯一识别 `openid` 不一样

**所以你不能把一个 bot 的 openid 用到另一个 bot 上。**

## 7. 消息事件与去重

### ⚠️ 相同 `msg_id` 可能重复推送

文档原文:

> 为确保消息可达,**相同 msg_id 可能重复推送**,开发者需结合 `msg_seq` 做去重。

**不去重就是重复回复。** 我们的做法:`msg_id → 首次见到的时间`,5 分钟窗口 + 500 条上限的 TTL 缓存。✅

### ✅ content 已被平台剥掉 @ 前缀

> `content` 字段**已自动去除@机器人的前缀**。

所以自己再剥一遍 `stripMentions` 是**双保险**,不是必需。但留着无害。

### ❌ 出站 @:群消息里**做不到**(2026-10-02 实测)

**结论:`<@!openid>` 放在群消息的 `content` 里不会被解析成提及。**

- 做法:加了一条 `/提及测试`,在群里发**一条**内容为 `<@!<发送者的 group_openid>> 提及测试…`
  的消息(出站默认剥 `@`,所以当时专门开了个 `keepMention` 例外口子把它放出去)。
- 结果:**用户没有收到任何 @ 提醒、消息里也没有 @ 标签** —— 消息发出去了,提及没生效。
- 官方文档里那句"`content` 里 `<@user_id>` / `<@!user_id>` 解析为 `@用户` 标签"出自
  **频道消息(子频道)**那一支([内嵌格式][fmt]);**群聊这条路上不成立**。
  (群聊发送那一页当时因域名解析失败未取得，因此该结论的证据边界是当时的实测。)
- **所以**:`sanitizeOutgoingText()` 对 `<@!…>` **一律剥掉、不留任何例外**;要叫某个人
  就**在正文里写名字**(钓鱼那条用 `namePrefix()`,出来是「示例成员，上钩了！」)。
  `keepMention` 那个口子**已删除**,`/提及测试` 也已删除。

[fmt]: https://bot.qq.com/wiki/develop/api-v2/server-inter/channel/message/format.html

### ✅ 群聊**真 @ 的官方语法是 `<qqbot-at-user id="…" />`**(2026-10-23 查证,还没接线)

- 官方「文本交互」页原文:群聊/文字子频道**支持含文本文字的消息类型**(文本 / 图文 / markdown),
  「@某人」的嵌入格式是 **`<qqbot-at-user id="" />`**;旧的 `<@userid>` **即将弃用**,
  「客户端展示为 @用户 标签」。纯文本、图文消息、markdown 消息三选一。
  URL: https://bot.qq.com/wiki/develop/api-v2/server-inter/message/trans/text-chain.html
- **发送侧口径要对齐**(2026-08 之后的群发接口):`msg_type` 只有 **0=文本 / 2=Markdown / 7=富媒体**;
  只有 0/2 有 `content` 字段,**7(图片/语音/视频)没有 content** —— 所以图片本体**带不了 @**,
  真 @ 只能搭**文本消息**;markdown(2)要模板权限(错误码 304036 / 40034127),别走。
- 我们的现状:**没接线**(`src/` 全仓无 `<qqbot-at-user>`)。已实测 `sanitizeOutgoingText()`
  **不会**剥它(它只认 `<@!…>` / `[CQ:at,…]` / 开头 `@昵称`);但**整条只剩标签**会被
  「整行只剩 HTML/XML 标记」判成泄漏剥空 ⇒ 接的时候标签必须跟正文同一行。
  落地要点(接在 `sendChunked()` 的 `mentionId` 选项上):openid 用**本群 member_openid**
  (`message.mentions[].id` / `senderId` / `person` 表),只拼到**第一块** content,并且走**被动回复**
  (带 `msg_id`;主动消息在部分群直接 40034105)。这里记录的是待验证的接线要点，不是已经实现或通过实测的能力。

### 🖼️ 「她好像 @ 到我了」≠ 真 @:那是**被动回复的客户端渲染**(2026-10-23 现场定性)

- 现象(历史部署观察，2026-10-23；群与成员名称已中性化):机器人发图片时,消息看起来 @ 到了请求者。
- 事实:**桥从来没有发过 @ 语法** —— 图片出口(`src\qq.js` 的 `sendMedia`)payload 只有
  `msg_type:7 + media.file_info (+msg_id/msg_seq)`,**没有 `content` 字段**;出站留痕
  `data\<bot>\state.db` 的 `outbound`(30 天 160 行)里也**没有一条**以 @ 开头或带
  `<qqbot-at-user>` / `<@…>` / CQ 码。`src/` 全仓也没有任何地方写 `message_reference`。
- 机制:发图走的是**被动回复**(`msg_id` + `msg_seq` 1..5,见 `src\meitu-service.js`),
  即"回复操作者那条 @ 消息" —— 客户端把它渲染成**引用/回复样式**,看起来像 @。
  第三方 SDK(simbot)文档也写「平台可能会自动添加 @目标 效果」;⚠️ **腾讯官方文档没有这句**,
  官方只定义"带 `msg_id` = 对那条消息的回复",客户端怎么渲染**没有官方文本**。
- 以前"主动 @ 用户"失败的**两条错路**:① 文本语法用错 —— `<@!openid>` 是**频道**写法,
  群聊不解析(上一节 2026-10-02 实测);② 走主动消息(不带 `msg_id`)—— 没有原消息可挂,
  既不会出现引用渲染,部分群还会直接 40034105。
- **区分"真 @"的唯一硬判据**:**有没有「有人@我」的系统提醒**;引用块/蓝标样式只是渲染,
  不能当证据。真 @ 的验证方法 = 用上一节的 `<qqbot-at-user>` 语法发一条**文本被动回复**对照。

### 被动回复的条数与时效(官方原文,2026-10-23 复查)

- 发送群聊消息页:`msg_id` = 被动回复的消息 ID(取自 `GROUP_AT_MESSAGE_CREATE` 等事件的 `d.id`,
  **5 分钟内有效**);`msg_seq` = 回复序号(与 `msg_id` 联合使用,默认 1;相同 `msg_id + msg_seq`
  重复发送会失败)。
  URL: https://bot.qq.com/wiki/develop/api-v2/autogen/api/v2_groups_group_openid_messages.post.html
- 消息收发概述「频率与时效」:群聊 **5 分钟 / 最多 5 次**,单聊 60 分钟 / 4 次;「被动消息」的
  定义就是"携带 `msg_id` 的对用户消息的回复"。
  URL: https://bot.qq.com/wiki/develop/api-v2/server-inter/message/overview.html
- ⚠️ 所以**文本回话与图片共用同一个 `msg_id` 的 seq 1..5**(`meitu-service.js` 的 `startSeq`);
  名额用完就退主动消息,在 `allow_proactive_msg=false` 的群就是 40034105(`bridge.log` 的
  「被动回复名额(seq 1..5)已用完」就是这一步)。

### 生命周期事件别丢

`GROUP_ADD_ROBOT`(被拉进群)、`GROUP_DEL_ROBOT`、`GROUP_MSG_REJECT`(**群管理关闭了机器人通知**)、
`FRIEND_ADD/DEL`、`C2C_MSG_REJECT`。

**`GROUP_MSG_REJECT` 尤其重要** —— 它意味着这个群从此收不到任何消息,不打印出来会让人以为是代码坏了。

## 8. 图片与附件

`attachments[]` 字段 📄:

| 字段 | 说明 |
|---|---|
| `content_type` | `image/jpeg` `image/png` `image/gif` / `voice` / `video/mp4` / `file` |
| `url` | 下载地址 |
| `filename` `width` `height` `size` | 元信息 |

### ❓ 未验证:QQ 表情包

**QQ 表情(表情包)是否走 `attachments[]` 的图片通道,没有验证过。**
`content_type` 枚举里只有 jpeg/png/gif,所以表情**可能**是 ARK 卡片或 `msg_elements` 里的另一种结构。

**想验证的方法:让人在群里发一个表情包,看日志里 `图片=` 是不是 0。**
如果是 0,那"偷表情包"这类玩法就走不通。

### 发图要先上传

发送图片不是直接给 URL,而是:

1. 上传文件到 `/v2/groups/{group_openid}/files`(推荐分片上传)📄
2. 拿到 `file_info`(**有时效 `ttl`**)
3. 用 `msg_type: 7` + `media.file_info` 发送

**单聊和群聊的上传接口不互通。** 📄

### ✅ 实测(2026-09-28):URL 直传可用 —— 转发媒体**不需要我们自己下载**

`POST /v2/groups/{group_openid}/files` 支持两种上传方式,**我们关心的是第一种**:

| 方式 | 请求 | 谁去拿文件 |
|---|---|---|
| **URL 直传** | `{file_type, url, srv_send_msg:false}` | **平台自己去下载转存** |
| 分片上传合并 | `upload_prepare` → 逐片 PUT → `upload_part_finish` → 带 `upload_id` 合并 | 我们上传(大文件才需要) |

`srv_send_msg:false` 只返回 `file_info`(不占主动消息频次),然后再调
`POST /v2/groups/{openid}/messages` 带 `{msg_type:7, media:{file_info}}`。
→ **一条媒体转发 = 2 次 API 调用,零下载、零落盘。**

类型与大小(📄 官方规格):

| `file_type` | 格式 | 软限 | 硬限 |
|---|---|---|---|
| 1 = 图片 | **png / jpg** | 20MB | 200MB |
| 2 = 视频 | mp4 | 30MB | 200MB |
| 3 = 语音 | silk | 20MB | 200MB |
| 4 = 文件 | 任意 | 200MB | 200MB |

⚠️ 三条容易踩的:
- **图片只吃 png/jpg** —— `image/gif` / `image/webp` 不在里面(docs §8 的 `content_type` 枚举里有 gif,
  但**上传**这一侧不收)。转发 gif 要么降级成 `file_type:4`(文件),要么跳过。
- **超过软限会自动降级成"文件"类型**,超过硬限报 `850031`。
- `40093002 超过今天发送文件容量上限` —— 媒体转发有**按天**的容量上限,不是只有条数上限。
- 上传接口频率 **50 QPS**;`850026` 表示"平台去下载那个 URL 失败"。

### ✅ 实测:群里发消息的两个"内容级"拦路码

| 码 | 含义 | 对我们的意义 |
|---|---|---|
| `40034006` | 消息内容违规 | 平台会**审出站内容**;被拒算在这只机器人头上 |
| `40054010` | **不允许发送URL** | 正文里带链接的消息可能**整条**发不出去 —— 转发时要先把 URL 抠掉或改写 |

> ⚠️ 与 §11 连起来读:**"自动转发群友的图文/视频"这件事,合规成本在机器人账号上**
> (运营规范 §5.1 要求机器人自带违规内容过滤),而平台的审核只是最后一道闸。

## 9. 主动消息 vs 被动消息 —— 配额完全两套

| 类型 | 特征 | 限制 |
|---|---|---|
| **被动**(回复) | 带 `msg_id` | 单聊 60 分钟 / 4 次;群聊 **5 分钟 / 5 次** 📄 |
| **主动** | 不带 `msg_id` | 见下表 |
| **互动召回** | `is_wakeup=true` | 用户对话后 30 天内 4 个周期,每周期 1 条 📄 |

### 主动消息配额 📄

| 场景 | Bot 维度 | 单关系维度 | 每日上限 |
|---|---|---|---|
| 单聊(未认证) | 30/qpm | 20/qpm | 1000 条/用户 |
| 群聊(未认证) | 30/qpm | **20/qpm** | 1000 条/群 |

### 关键推论(决定了我们几个设计)

1. **被动回复窗口 5 分钟** → 我们把单轮超时设成 **240 秒**,留 1 分钟余量
2. **对没 @ 机器人的消息发言 = 主动消息** → 所以"自发发言"必须节流,不能想发就发
3. **`msg_id` 会过期** → 过了就降级成主动消息(错误码见下)

### 同一消息多次回复要递增 `msg_seq` 📄

相同 `msg_id + msg_seq` 重复发送会失败。我们的分片发送就用递增 `msg_seq`。✅

### 过期/失效错误码

| 码 | 含义 |
|---|---|
| `40034005` | 回复消息 `msg_id` 已过期 |
| `304103` | 消息 ID 已过期,不能回复 |
| `304026` / `304027` | MSG_ID 错误 / 回复的消息过期 |
| `40034128` | 被动回复时间或次数超限 |
| `40054005` | 消息被去重(检查 `msg_seq`) |
| `40054007` | 消息长度超限 |

## 10. 平台没有的东西

| 想做的事 | 现实 |
|---|---|
| 改机器人头像/昵称 | **没有 API**。在开放平台控制台设,且**要过审核** 📄 |
| 让机器人"看见"群里的历史消息 | 只能靠全量模式实时收,**没有拉历史消息的接口** |
| 私聊主动推送 | 用户可以关闭「允许主动发送」,关了就**一律失败** 📄 |
| **列出"这个机器人加入了哪些群"** | ✅ **实测(2026-09-28):没有这个接口。** 群清单只能从"收到过的消息"里长出来(`known_group`)—— 所以**她在群里但还没收到过消息 = 我们不知道那个群存在**。补救:让授权成员在那个群 @ 机器人一次；如需人工补录，必须先通过平台信息核对群身份，不要把派生清单当成平台成员关系 |

> 最后一行是 2026-09-28 那次"示例群到底在不在她群里"的教训:
> 我拿 `known_group`(派生索引)当成了"她所在的群清单",于是把一个她明明在里面的群
> 判成了"她不在"。**派生索引不能当平台事实用**。

## 10.1 ✅ 群信息接口:文档说"仅白名单",历史部署曾可用

`GET /v2/groups/{group_openid}/info`(30 QPM):

```json
{ "group_openid": "…", "group_name": "示例群", "group_finger_memo": "",
  "group_class_text": "", "group_tags": [], "group_member_num": 5 }
```

`GET /v2/groups/{group_openid}/bot_state`:

```json
{ "member_openid": "…", "joined_at": "2026-09-28T12:01:36+08:00",
  "allow_proactive_msg": false, "recv_msg_setting": "all", "member_role": "member" }
```

**这两条改变了几件事**:

1. **群名可以拿到了** —— `/群列表` 因此能显示群名 + 人数(平台群信息接口),不必再对着 `A1000000…` 猜。
2. **`recv_msg_setting` 就是"全量消息打开没有"的平台侧判据**:`all` / `only_mention` / `""`。
   历史实测（使用中性占位群名）:同一个机器人,`<group-A>` 是 `all`,`<group-B>` 是 `only_mention`,
   `<group-C>` 一开始是 `""`。**用户把群设置一开,它当场变成 `all`** ✅
3. **`allow_proactive_msg` 解释了 `40034105`**:它是**逐群**的,不是"这只机器人没有权限"。
   历史实测同一时刻:`<group-C>` = `false`(发不了)、另两个群 = `true`(有成功发送记录)。
   → 不应由一个群的拒绝推断“机器人在所有群都没有主动消息权限”；应逐群核对
   `allow_proactive_msg`，并保留实际返回值。

⚠️ 错误码 `11253`("应用无接口访问权限,仅白名单机器人可用")是**文档写的**;
历史部署没有被该错误码拒绝 —— 但**换机器人/换群时仍需由部署者独立验证**,别假定一定可用。本轮文书整理没有重新请求平台。

> 第三方能改头像的插件(如 `astrbot_plugin_qqprofile`)标注的是**「仅 aiocqhttp」** ——
> 那是控制真实 QQ 账号的方案,官方机器人**没有这回事**。

### ✅ 实测(2026-09-28):「聊天记录」卡片会被**展平成纯文本**,而且**嵌套的内容会消失**

用户在私聊里合并转发一条「群聊的聊天记录」,到达事件里的 `content` 是**6801 字的纯文本**:

```
[群聊的聊天记录]
=== 消息 1 ===
[发送者] 某人
[附件1] 类型:图片 文件名:xxx.jpg 尺寸:1280x1707 大小:157.4KB URL:https://multimedia.nt.qq.com.cn/download?appid=…&fileid=…&rkey=…
```

四条判据:

| 事实 | 说明 |
|---|---|
| **群事件也会展平** | 群里的记录同样以纯文本到达(实测 `文字=6839`),所以"搬运"不必依赖人工转发 |
| **标题不固定** | `[群聊的聊天记录]` / `[示例会话的聊天记录]` —— 别写字面量 |
| 🔥 **嵌套的记录只剩空块** | 一条"第一层图 + 里面夹着很多嵌套"的记录 = 15 个消息块里 **11 个空块**(只有 `[发送者]`,内容没了)。**嵌套内容不在文本里,拿不到** |
| **全嵌套的记录根本没投递** | 用户发的那条"完全是嵌套聊天记录"在日志里**没有任何到达记录** |
| **附件只有元信息 + URL** | 图片正文不在文本里;URL 是 `multimedia.nt.qq.com.cn` + `rkey`(临时鉴权,**实测 5 分钟后仍可用**,有效期未测) |

> ⚠️ 对"转发记录"这件事的直接含义:**只搬"0 空块 + 纯图/文字"的记录**,
> 有任何空块就说明内容已被吞掉 —— 那时候打出来的文件会**静默丢内容**,比不做更糟。

### ✅ 实测:那串 `rkey` URL 可以直接喂给上传接口

`POST /v2/groups/{id}/files` 带 `{file_type:1, url:<记录里的URL>, srv_send_msg:false}` →
**平台自己去下载转存**,返回 `file_info`(`ttl=86400`,比文档示例的 300 秒宽得多)。
即"转发媒体"**不需要我们自己下载**;但本地组装的文件(比如 PDF)只能走**分片上传**。

## 11. 合规红线(影响能不能活下来)

来自[运营规范](https://bot.q.qq.com/wiki/business/):

| 条款 | 内容 |
|---|---|
| §2 基本信息 | 名称/头像/简介**都要过审核**。头像**含水印、二维码、联系方式**会被拒 |
| §2 | **不得侵犯他人知识产权** —— 用动漫官方图当头像有驳回风险 |
| §5.1 内容安全 | 机器人**必须自带违规内容过滤机制**,否则封禁搜索/添加能力直至下架 |
| §6.1 | 违反法律法规的内容 → **永久封号** |
| §6.2 | **色情低俗内容** → 按程度处理 |
| §5.10 数据安全 | 收集用户数据需告知同意;终止服务后 24 小时内删除 |

**对角色扮演机器人最现实的两条风险:**

1. **头像侵权**(用了别人的画)→ 头像被清空
2. **不加过滤地转发用户内容**(比如自动重发群友图片)→ 内容安全条款

## 12. 换到其他平台时,把这一页重新问一遍

这份清单比上面的正文更耐用 —— **换平台时照着问,能少踩一半的坑**:

- [ ] **凭证有几个?** 哪个是密码,哪个不是?
- [ ] **拿到 token 后,失败时 HTTP 状态码还是 200 吗?** (QQ 是,吃了亏)
- [ ] **网关/回调地址是固定的还是动态获取的?**(QQ 文档写错的地址,实际是另一个)
- [ ] **事件推送是 WebSocket 还是 Webhook?** 需要公网地址吗?需要验签吗?
- [ ] **有没有"全量消息"这种东西?开关在哪?谁能开?**(QQ 在群设置,群主,逐群)
- [ ] **一共有几个 id 空间?它们能互相比较吗?**(QQ 有四个)
- [ ] **消息会重复推送吗?** 去重键是什么?
- [ ] **主动发消息和回复消息的配额分别是多少?**
- [ ] **回复有有效期吗?多久?**
- [ ] **平台有没有"改资料"的 API?还是要过审核?**
- [ ] **有没有平台专属的内容红线?违反的后果是什么?**
- [ ] **第三方库的文档和官方文档,哪个更准?**(QQ 这次是第三方更准)
