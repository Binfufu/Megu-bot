# 架构与适配器契约

> 这份文档回答一个问题:**要把这套东西搬到另一个聊天平台,哪些能直接复用,哪些必须重写?**
>
> 结论先行:**13 个源文件里只有 1 个是平台专属的。** 骨架已经在那儿了,只是之前没被显式写下来。

---

## 1. 两层进程模型

```
┌─────────────────────────────────────────┐
│ 聊天平台(QQ / Telegram / Discord / …)   │
└───────────────┬─────────────────────────┘
                │  平台协议(WebSocket / Webhook / 轮询)
                │  平台鉴权、平台消息格式
┌───────────────▼─────────────────────────┐
│ bridge 进程(Node)                       │
│  ├─ 平台适配层  ← 换平台时改这里         │
│  ├─ 会话与策略层 ← 通用,直接复用         │
│  └─ agent 驱动层 ← 通用,直接复用         │
└───────────────┬─────────────────────────┘
                │  DSH SDK 协议(stdio 上的换行分隔 JSON-RPC 2.0)
┌───────────────▼─────────────────────────┐
│ dsh --profile <名字>  (子进程)          │
│  └─ 模型 + 工具 + 会话持久化             │
└─────────────────────────────────────────┘
```

### 为什么分成两个进程

| 好处 | 说明 |
|---|---|
| **崩溃隔离** | agent 跑飞了不会带走平台连接;bridge 挂了 agent 子进程也会被回收 |
| **各自的语言生态** | bridge 可以换成 Python/Go,只要说 SDK 协议 |
| **可单独重启** | 改角色卡只需重启 bridge 的子进程 |
| **协议是稳定的** | SDK 协议只有 3 个方法 + 4 个通知,比任何平台 API 都稳 |

### 为什么 agent 不用 HTTP 接口

**SDK 协议是 stdio 上的 JSON-RPC**,不是 HTTP。原因很简单:

- **一问一答、且回复必须流式回来** —— WebSocket 需要额外的连接管理,HTTP 需要公网端口
- **父子进程关系天然提供了生命周期绑定** —— bridge 死了,dsh 自动跟着死
- **不需要任何端口和鉴权** —— 不暴露网络面

> 📌 这是**唯一稳定不变的接缝**。平台 API 会变、会废弃、会写错文档;**SDK 协议这一层不会**。

## 3. 适配器契约:一个新平台必须提供什么

> ⚠️ **这是契约描述,不是代码。** 现在只有一个平台实现,过早抽象会抽错。
> 等第二个平台真做了,重复的部分会自己浮出来。**这一节是"到时候照着填"的清单。**

### 3.1 必须实现的四件事

#### ① 令牌获取与刷新

```
输入:平台凭证(从 .env 读)
输出:一个可用的令牌
要求:
  - 自己缓存,不要每次请求都换
  - 提前一小段时间刷新
  - 业务失败要能识别(注意:失败时 HTTP 状态码可能仍是 200)
```

对应 `qq.js` 的 `TokenManager`:带 `#expiresAt`、`#inflight`(并发去重)、`#refresh()`。

#### ② 事件流

```
输入:平台推送的事件
输出:调用 onMessage(统一 message) / onLifecycle(通知)
要求:
  - 长连接要保持(心跳 + 重连 + 恢复)
  - 重复推送要去重
  - 认不出来的事件要打日志,不能静默丢
```

三种平台模型,差异全在这里:

| 模型 | 例子 | 难点 |
|---|---|---|
| WebSocket 长连接 | QQ、Discord | 心跳、重连、Resume、分片 |
| Webhook 回调 | 飞书、企业微信、Slack | **需要公网地址**、验签、幂等 |
| 轮询 | 老式 API | 延迟、浪费、去重 |

#### ③ 发送消息

```
输入:目标会话 id + 文本(+ 媒体)
要求:
  - 区分"回复"(有触发消息 id)和"主动发送"
  - 认证失败/配额超限要报出可读的错误
  - 超长要分片,且分片不能互相覆盖
```

`qq.js` 的 `QqApi`:注意它把 `msg_id`(被动)和 `msg_seq`(分片序号)分开处理。

#### ④ 媒体下载

```
输入:平台给的媒体描述(可能是 url / file_id / 加密 blob)
输出:base64 + mimeType
要求:
  - 有大小上限,先看元信息再下载
  - 有超时
  - 下载失败不能连累文字部分
```

`images.js`:注意 `fetchImageBlocks` 是**逐张容错**的 —— 一张失败不影响其他张和文字。

### 3.2 统一数据结构:归一化后的消息

**这是整个契约的核心 —— 归一化一旦完成,上面的策略层全部复用。**

```
message = {
  scene:      'c2c' | 'group'        // 私聊还是群聊
  targetId:   string                 // 回复要发给谁(会话 id)
  senderId:   string                 // 发送者 id(用于访问控制)
  senderName: string                 // 显示名(用于上下文渲染)
  messageId:  string                 // 平台消息 id;主动发送时为 undefined
  content:    string                 // 已剥掉 @ 前缀的纯文本
  images:     [{ url, mimeType, size, ... }]
  isMention:  boolean                // 是否明确指向机器人
  timestamp:  string
}
```

**只要新平台能产出这个结构,以下全部零修改复用:**

- 访问控制(白/黑名单)
- 场合标记(`[私聊]` / `[群聊]`)
- 关键词触发、第二人称识别
- 对话窗口、双冷却、自发发言闸门
- 定时暖群、定时问候
- 图片转 base64 送模型
- 出站清洗(@ 剥离、名字前缀剥离、切分)

### 3.3 策略层:所有平台都需要的那几个概念

这些是从 QQ 实践中提炼的,**与平台无关**,新平台照抄:

| 概念 | 为什么通用 |
|---|---|
| **对话窗口** | 任何 IM 里,人不会每句都叫名字 |
| **双冷却**(被搭话 / 无人搭话) | 任何平台都有"主动发送配额"这个问题 |
| **防抖**(等安静再回) | 任何群聊都是一串一串消息 |
| **睡眠时段** | 半夜发言在任何平台都讨人厌 |
| **定时任务三道闸门** | 时钟驱动的调用在任何平台都要保守 |
| **配置写错 fail closed** | 安全默认值在任何平台都成立 |

## 4. DSH 侧的三个关键事实

搬平台时**这一层完全不用动**,但必须理解,否则会踩坑。

### 4.1 profile 必须包含 SDK 服务

profile 的 bundles 要含 `@deepseek-ai/dsh-sdk-app`,否则它不会响应 SDK 请求。

`$DSH_HOME/profiles/<名字>/package.json`:

```json
"bundles": ["@deepseek-ai/dsh-base", "@deepseek-ai/dsh-sdk-app"]
```

### 4.2 🔥 会话 id 是"创建键",不是"恢复键"

SDK 协议里 `session/prompt` 的 `sessionId` 由**客户端提供**,未知 id 会**懒创建**。
但服务端对每个 id 都调 `agents.create({sessionId})`,而**注册表会拒绝一个已被历史进程持久化过的 id**。

**后果:同一个 id 跨进程复用会报 `already exists`。**

**我们的对策:会话代数。** 第一代用裸 key,之后每次 bridge 重启 +1:

```
qqbot-group-<群id>  →  -g2  →  -g3  →  …
```

代数**持久化在状态文件里**,所以重启时直接跳到下一代,不用先失败一次。

> **代价:bridge 每重启一次,该会话的上下文从头开始。** 这是 SDK 的限制,不是 bug。

### 4.3 🔥 `dsh` 拒绝 `.env` 里的 `DSH_*` 变量

`dsh` 有保护:它发现的**所有 `.env` 文件都不允许设置任何 `DSH_*` 变量**
(因为这类变量决定进程如何启动、代码从哪加载、流量走哪条路)。

**所以 bridge 自己的配置一律用 `QQBOT_` 前缀**,再由 bridge 翻译:

| 我们怎么传 | 不用环境变量的原因 |
|---|---|
| profile → 子进程 **argv** | 命令行参数 |
| 工作目录 → 子进程 **cwd** | spawn 选项 |
| 模型路由 → **JSON-RPC 握手** | initialize 参数 |

**一个都不需要以环境变量形式传给孩子进程。**

### 4.4 🔥 子进程 cwd 下的 `.env` 会进 agent 的环境

`dsh` 会读**自己 cwd 下的 `.env`** 并把值并入 agent 的环境。

**如果 agent 工作目录就是 bridge 目录,那 `.env` 里的 `QQ_CLIENT_SECRET` 就会进 agent 的运行环境** —— 而 agent 能执行任意命令读到它。

**两层防御:**

1. agent 工作区默认放在 bridge 目录**之外**
2. 派生子进程时**剥掉** `QQ_APP_ID`、`QQ_CLIENT_SECRET` 和所有 `QQBOT_*`

## 5. 运行与运维

### 5.1 启动链

```
bots\<bot>\run.cmd  (ASCII-only,chcp 65001)
   └─ node scripts/launch.js        ← 环境自检 + 中文报错
        └─ src/index.js main()      ← 编排
             └─ spawn dsh --profile qqbot
```

> ⚠️ **不要叫 `start.cmd`** —— cmd.exe 有内置的 `START` 命令,从 shell 调用时会被遮蔽,
> 报出莫名其妙的 `The system cannot find the file .cmd.`

### 5.2 自检与诊断工具

| 脚本 | 用途 | 需要网络/模型 |
|---|---|---|
| `selftest.js` | 全部纯逻辑单测（**数量现算，别抄**：跑一次看它自己的 PASS 行 —— D34） | 否 |
| `verify-qq.js` | 只验 QQ 链路(换 token + 连网关 + READY) | 网络,不调模型 |
| ~~`verify-dsh.js`~~ | **已随 6B 去 DSH 化退役**（桥不再起 `dsh` 子进程）；要离线验一轮角色/模型改用 `card-eval.js`（走 `src\isolated-turn.js` 的临时库） | — |
| `warmup-status.js` | 暖群排期:各群下次到期时间 | 否 |
| `usage-report.js` | token 用量(区分新增/缓存输入) | 否 |
| `context-report.js` | **当前会话的上下文占用** | 否 |
| `inspect-session.js` | 单会话结构探查 | 否 |
| `session-log.js` | **库**:解压 DSH 会话日志(多帧 zstd) | 否 |

### 5.3 一个值得复用的技术点:多帧 zstd 的解压

DSH 会话日志是**多个独立 zstd 帧的标准拼接**(一个 header 帧 + 每个写入批次一帧)。

- `zlib.zstdDecompressSync()` **只解第一帧**
- `zlib.createZstdDecompress()` 流式解码**直接报 `ZSTD_error_prefix_unknown`**

**对策**(`scripts/session-log.js`):按 zstd 魔数 `28 B5 2F FD` 手动切帧,
**切点只有在真的解得开时才被信任** —— 所以压缩数据里出现同样的字节也不会带偏扫描。

> 这是个通用的"**带回溯的扫描**"模式:先乐观切分,失败就往后找下一个候选点。

## 6. 搬到新平台的成本估算

| 工作 | 复用? | 估计 |
|---|---|---|
| 适配器(4 件事:令牌/事件/发送/媒体) | 重写 | **主要成本** |
| 归一化成统一 message | 重写(但要产出同一结构) | 小 |
| `index.js` 编排 | 改接线,骨架不动 | 小 |
| 9 个平台无关文件 | **零修改** | 0 |
| 测试 | 纯逻辑测试**全部复用** | 0 |
| 平台对抗手册 | **照第 12 节重新问一遍** | 中 |

**老实说:模板能把你从 0 带到 60%,到不了 100%。** 剩下 40% 是每个平台独有的怪癖,
**只有真做了才知道** —— 就像 QQ 的全量模式藏在群设置里。

## 7. 如果真要抽象,什么时候做

**现在不要做。** 只有一个实现的时候抽出来的接口,几乎必然是为这个实现量身定做的。

**触发条件:做完第二个平台。** 那时候:

1. 两个适配器**并排放**,重复的部分自己会浮出来
2. 抽象出来的是**真正的共性**,不是猜测
3. `index.js` 里那些 QQ 假设,会在第二次接线时暴露无遗

这就是"**三次法则**":重复三次之后再抽象。现在是一次,连两次都不到。
