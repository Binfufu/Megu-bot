# 架构与适配器契约

> 这份文档回答一个问题：**要把这套东西接到另一个聊天平台，哪些能直接复用，哪些必须重写？**
>
> 结论先行：**平台专属代码集中在一个文件（`src/qq.js`）**；归一化之后的准入、节奏、回合、记忆、出站都在通用层。接新平台的成本主要是"一个适配器 + 一次接线"，不是重写整个 bot。
>
> 架构总览（三区、模块边界、一条消息怎么走）见 [公开架构说明](<37-公开架构说明.md>)；本文只讲两件事：**当前进程模型**与**适配器契约**。
>
> 共享与隔离边界的权威口径（公开集视图）见 [边界契约（公开集视图）](<16-边界契约-公开版.md>)；状态归属与交回机制不在本文重复。

**范围声明**：本文描述公开集里的代码结构，不描述私有部署，也不承诺公开集未包含的能力。行为以当前代码与测试输出为准；文档与代码不一致时，先按代码判断，再提 PR 修文档或代码。

## 1. 当前进程模型：单进程 + 自有引擎

```text
bots/demo/run.cmd            纯 ASCII 启动包装器（定位仓根、显式选 .env）
  └─ scripts/launch.js       Node 版本 / 配置文件 / bot home 预检，中文报错
       └─ src/index.js main()   装配：状态库、模型配置、单实例锁、通道、后台定时
            ├─ src/qq.js                 平台适配（QQ）
            ├─ src/engine.js             回合内核（自有引擎）
            ├─ src/llm.js                模型客户端（OpenAI 兼容 HTTP）
            ├─ src/sqlite-store.js       状态库
            ├─ src/memory-store.js       记忆库
            └─ scripts/meitu-fetch-one.mjs  搬图抓取（仅启用搬图时出现）
```

几句话说完：

- **只有一个常驻 Node 进程**。平台事件从一条**出站 WebSocket 长连接**进来；模型调用是本进程发出的普通 HTTP 请求。没有独立的 agent 子进程，也没有本地 RPC 握手。
- **生命周期**：`main()` 装配完、把网关挂上就返回，进程靠网关连接保活；退出只走几条明确的路——`SIGINT`/`SIGTERM`、重启请求、启动或运行异常。`scripts/launch.js` 里记了这条设计踩过的两个真实事故（"main 返回后静默退出"与"用大退出码表示重启不成立"），改动退出路径前值得先读。
- **子进程只在几个明确边界出现**：搬图抓取（`src/meitu-service.js` spawn `scripts/meitu-fetch-one.mjs`，网络与落盘隔离在那里）、可选的守护进程（`src/supervisor.js` 起 `launch.js`）、模型 key 的 DPAPI 解密（`src/secret-box.js` 调 PowerShell）等。它们都是短生命周期工具，**不构成第二个常驻运行时**；少数可选能力依赖本机外部程序，缺件时按明确报错处理，不会用空功能假装可用。
- **历史**：早期版本是"bridge 进程 + 独立的 agent 子进程（stdio 上的 JSON-RPC）"的双进程模型。该模型已退役，旧文档里关于子进程协议、profile、子进程环境变量的内容不再适用；历史设计记录只留在维护仓，不随公开集分发。

| 层 | 代表文件 | 职责 |
|---|---|---|
| 入口与装配 | `scripts/launch.js`、`src/index.js`、`src/config.js`、`src/bot-home.js`、`src/lock.js`、`src/log.js` | 环境预检、配置解析、单实例锁、装配与主循环 |
| 通道适配 | `src/qq.js`、`src/channel-policy.js`、`src/group-context.js`、`src/images.js`、`src/safe-download.js` | 鉴权、事件、发送、媒体；通道容量与过期口径 |
| 回合内核 | `src/engine.js`、`src/llm.js`、`src/context-budget.js`、`src/turn-policy.js`、`src/commands.js` | 上下文装配与裁剪、模型调用、命令分流 |
| 状态与记忆 | `src/sqlite-store.js`、`src/memory-store.js`、`src/burst-queue.js`、`src/memory-archive.js` | 会话与数值、轮次与摘要、连发合并 |
| 出站 | `src/index.js` 的 `sendChunked()`、`src/qq.js` 的 `QqApi` | 清洗 → 分片 → 被动/主动发送 → 留痕 |

更细的文件级边界表（目录 → 职责 → 依赖方向）在 [公开架构说明](<37-公开架构说明.md>) 第 4 节，本文只点到"层"。

## 2. 哪些是平台专属，哪些能复用

**平台专属集中在 `src/qq.js`**：令牌、OpenAPI 调用、网关状态机（心跳 / 重连 / Resume）、事件归一化、QQ 出站清洗。运行代码里只有 `src/index.js` 静态 import 它（`scripts/` 下的连通性检查与自测脚本也会 import，那是测试用途）——可以直接用 grep 核，不需要信任本文。

其余模块与平台无关：回合内核、模型客户端、上下文预算、状态库与记忆库、连发合并、通道策略数据、命令表、搬图子系统。它们只认归一化之后的 `message` 与自己的状态。

**但"平台无关"不等于"已经解耦"**：`src/index.js` 的接线仍带 QQ 假设（会话键、`msg_id`/`msg_seq`、@ 语义、平台配额）。现在只有一个平台实现，`index.js` 没有为第二个平台提前抽象——真要接第二个平台，正确顺序见第 6 节。

## 3. 适配器契约：一个新平台必须提供什么

> ⚠️ **这是清单，不是代码。** 现在只有一个实现，过早抽象会抽错；等第二个平台真做了，重复的部分会自己浮出来。

### 3.1 必须实现的四件事

#### ① 令牌获取与刷新

```text
输入：平台凭证（从本地 .env / 启动配置读）
输出：一个可用的令牌
要求：
  - 自己缓存，不要每次请求都换
  - 提前一小段时间刷新（QQ 侧是提前 60 秒）
  - 业务失败要能识别：平台可能用 HTTP 200 返回业务错误码，不能只看状态码
```

参考 `src/qq.js` 的 `TokenManager`：缓存过期时间 + 并发刷新去重（同一时刻只有一次换票）。

#### ② 事件流

```text
输入：平台推送的事件
输出：归一化的 message（见 3.2）与少量生命周期通知
要求：
  - 长连接要保活：心跳 + 断线重连 + 重放/恢复
  - 重复推送要去重（同一个 messageId 只处理一次）
  - 认不出来的事件类型要打日志，不能静默丢
```

三种平台模型的差异全在这里：

| 模型 | 例子 | 难点 |
|---|---|---|
| WebSocket 长连接 | QQ、Discord | 心跳、重连、Resume、分片 |
| Webhook 回调 | 飞书、企业微信、Slack | **需要公网地址**、验签、幂等 |
| 轮询 | 老式 API | 延迟、浪费、去重 |

QQ 侧对应 `QqGateway`：对外发 `message` / `memberJoined` / `ready` / `fatal` 几种事件，平台负载在内部转成统一 `message`；不是消息的事件返回 `null`。

#### ③ 发送消息

```text
输入：目标会话 id + 文本（+ 媒体）
要求：
  - 区分"被动回复"（带触发消息 id，通常不吃主动配额）与"主动发送"
  - 超长要分片，且分片序号不能互相覆盖
  - 认证失败 / 配额超限要报出可读的错误，不能静默丢
```

参考 `QqApi`：文本发送按会话走 `sendDirect` / `sendGroup`，把 `msg_id`（被动回复标记）与 `msg_seq`（同一条入站消息下的分片序号）分开处理；媒体先上传换 `file_info` 再发送。

#### ④ 媒体（下载 + 上传）

```text
输入（入站）：平台给的媒体描述（url / file_id / 加密 blob）
输出：base64 + mimeType
要求：
  - 先看元信息（类型 / 大小）再下载，有上限
  - 有超时；下载失败不能连累文字部分
输入（出站）：本地文件
要求：能上传成平台可发送的媒体引用
```

参考 `src/images.js`：`fetchImageBlocks` 是**逐张容错**的——一张失败不影响其他张和文字；类型只收 `image/png`、`image/jpeg`、`image/webp`、`image/gif`，单条最多 3 张，默认上限 10 MB / 15 秒。

### 3.2 统一数据结构：归一化后的消息

**这是整个契约的核心——归一化一旦完成，上面的策略层全部复用。**

```js
message = {
  scene:      'c2c' | 'group',     // 私聊还是群聊
  targetId:   string,              // 回复要发给谁（会话 id）
  senderId:   string,              // 发送者 id（访问控制用）
  senderName: string | undefined,  // 显示名（上下文渲染用；平台可能不给）
  messageId:  string | undefined,  // 平台消息 id；主动发送时为 undefined
  replyToMessageId: string | null, // 这条消息引用了哪条（没有就 null）
  content:    string,              // 已剥掉 @ / CQ 码 / 平台标记的纯文本
  images:     Array<{ url, mimeType, filename?, width?, height?, size? }>,
  isMention:  boolean,             // 是否明确指向 bot
  mentions:   Array<{ id, username, bot }>,
  timestamp:  string,
}
```

QQ 层还会在同一个对象上带几个平台语义位（`isPoke` / `isFace` / `mentionsOthers` 等）。**新平台不提供这些也能跑**——下游只依赖上面这份最小契约；额外字段是"该平台特有的表达"，消费方必须容忍缺省。

**只要新平台能产出这个结构，以下全部零修改复用：**

- 访问控制（白名单 / 黑名单；配置写错 fail closed，不因手误放宽）
- 场合标记（`[私聊]` / `[群聊]`）与第二人称识别
- 关键词触发、对话窗口、连发合并、双冷却、自发发言闸门
- 定时暖群、定时问候
- 图片转模型输入块
- 出站清洗（@ 剥离、名字前缀剥离、控制标记剥离）与分条

### 3.3 策略层：所有平台都会遇到的那几个概念

| 概念 | 为什么通用 |
|---|---|
| 对话窗口 | 任何 IM 里，人不会每句都叫名字 |
| 连发合并（防抖） | 任何群聊都是一串一串消息，等安静再回 |
| 双冷却（被搭话 / 无人搭话） | 任何平台都有主动发送的配额与打扰成本 |
| 睡眠时段 | 半夜发言在任何平台都讨人厌 |
| 定时任务的保守触发 | 时钟驱动的调用在任何平台都容易出问题；错过一拍要能说清"不补发" |
| 配置写错时 fail closed | 安全默认值在任何平台都成立 |

每条通道"满了怎么办 / 迟了怎么办"的成文口径见 [通道策略表](<17-通道策略表.md>)。

## 4. 契约在实现里的四个落点

### 4.1 归一化是一次性的接缝

`normalizeDispatch()` 一个函数负责：剥 @ 与 CQ 码、收附件、判"是否在叫 bot"、多 bot 同时被 @ 时的让贤。下游不再碰平台原始负载。新适配器要把自己的负载在**同一位置**收口——不要在业务层到处写 `if (平台 === …)`。

⚠️ 一个踩过的坑：判 @ 的证据要读**原始 payload**（归一化后的 `content` 已经把 `<@id>` 剥掉了）。新平台同理：归一化会丢掉的证据，必须在归一化那一层用完。

### 4.2 出站只有一个咽喉

所有真的发出去的消息都走 `src/index.js` 的 `sendChunked()`：清洗 → 按平台上限分片 → 带 `msg_id`/`msg_seq`（或主动发送）→ 写发送留痕。适配器只提供"发送一条"的能力；**分片、配额、清洗都在通用层**，这样"到底发了什么"永远只有一个答案。

被动回复一条入站消息最多 5 条；普通发言超量时并进最后一段、不转主动配额——口径见 [通道策略表](<17-通道策略表.md>)。

### 4.3 会话键是"会话"，不是用户身份

`conversationKeyFor(message)` 把消息映射到一个稳定会话键（私聊按对方、群聊按群），历史、记忆、冷却、数值都按这个键隔离。接新平台时必须能稳定回答"这条消息属于哪个会话"，否则记忆会串、冷却会错。

### 4.4 模型层只认 HTTP

`src/llm.js` 是唯一模型出口：OpenAI 兼容 HTTP、并发队列、退避重试、超时、错误分类、usage 带出。换平台不动模型层，换模型不动通道层；两边靠 `src/engine.js` 的回合接口相接（`initialize` / `runTurn` / `isBusy` / `resetConversation` / `stop` / `on`）。

## 5. 搬到新平台的成本

| 工作 | 复用？ | 说明 |
|---|---|---|
| 适配器（令牌 / 事件 / 发送 / 媒体） | 重写 | **主要成本** |
| 归一化成统一 `message` | 重写，但必须产出同一结构 | 小 |
| `src/index.js` 接线 | 改接线，骨架不动 | 小到中（QQ 假设会在这里现形） |
| 回合内核 / 模型客户端 / 状态与记忆 / 策略层 | **零修改** | 0 |
| 纯逻辑测试 | 大部分复用 | 需要补一个假的事件源 |
| 平台对抗手册 | 照 [平台对抗手册](<01-平台对抗手册-QQ.md>) 的问法重新问一遍 | 中 |

老实说：模板能把你带到"能跑"，到不了"能上生产"。剩下的是每个平台独有的怪癖，只有真做了才知道。

## 6. 如果真要抽象，什么时候做

**现在不要做。** 只有一个实现的时候抽出来的接口，几乎必然是为这个实现量身定做的。

**触发条件：第二个平台真的做完。** 那时候：

1. 两个适配器并排放，重复的部分自己会浮出来；
2. 抽出来的是**真正的共性**，不是猜测；
3. `src/index.js` 里那些 QQ 假设，会在第二次接线时暴露无遗。

正确顺序是：先把"事件源"做成同一种形状、让下游只认统一结构，再回头抽公共接口；不要凭空设计一套通用适配器。
